# Current Best Profiles

This is the maintained snapshot of BaseLayer's current best-known runtime profiles and benchmark numbers. Update this file when a newer valid artifact supersedes a row.

Rules:

- Prefer valid BrowserArena semantics for comparisons: Google target, `domcontentloaded`, no request blocking, and raw artifact linked.
- Separate main Chromium-compatible paths from experimental fast lanes.
- Optimize for total lifecycle and success rate, not only `page_goto_ms`.
- Treat the **primary profiles** as the **fastest reliable configurations** of each active family, not just the most recent script default that happened to be exercised.
- For Firecracker latency-facing comparisons, that means the canonical `baselayer-firecracker-headless-shell` configuration includes **async delete** unless a doc explicitly says a run was a sync-delete diagnostic.
- When a row is superseded, keep the old result in the relevant result doc or [optimization-experiments-log.md](./optimization-experiments-log.md), but update this file to the new best.

## Current Default Recommendation

- Use Firecracker + `chromium-headless-shell` for the main BaseLayer product path.
- Use `1 vCPU`, `1024 MB` for high-density BrowserArena-style AWS bare-metal runs unless a newer artifact proves otherwise.
- Use **async delete** for the canonical `baselayer-firecracker-headless-shell` latency/leaderboard path. Treat sync delete as a separate strict-recycling diagnostic mode, not as the primary configuration.
- Do not use `waitUntil=commit` or Playwright request blocking for BrowserArena/Google comparisons.
- Treat full Chromium, Lightpanda, and fluid compute as separately labeled experimental lanes.

## Suggested Next Optimizations

These are concrete targets prioritized by expected impact on the current bottleneck (`page_goto_ms` and create/connect at `c24+`), and by what is already implemented but unverified.

1. **Build a PGO-enabled custom `headless_shell` before judging more Chromium source patches.** Stock Playwright shell is expected to be PGO-optimized; our source builds so far are non-PGO. The next fair source-build experiment is `headless-buildable-v1` with `BASELAYER_CHROMIUM_PGO_PHASE=1`, representative training, then `BASELAYER_CHROMIUM_PGO_PHASE=2` with `BASELAYER_CHROMIUM_PGO_DATA_PATH`. See [goto-optimization-deep-plan.md](./goto-optimization-deep-plan.md).
2. **If fluid compute is revisited, narrow the hypothesis before spending more metal.** The mixed active/idle rerun on 2026-04-21 removed the old `cpu.weight` permission ambiguity and still lost: `Raticate` beat both `Spearow` and `Nidoran-M`. The next fluid attempt should not be another broad rerun of the same profiles; it should target one concrete knob such as lower scheduler-transition frequency, a different active/idle threshold, or a less aggressive cgroup weight spread.
3. **Stack the small but proven wins into one profile.** `baselayer-firecracker-headless-shell-startup-prune` shaves about `342 ms` total / `389 ms` goto at `c24` vs. baseline. `thp-always` shaves another `18-55 ms` goto. CDP-only warm shaves `~190 ms` goto but regresses create by `~240 ms`. None of these are individually a breakthrough, but a stacked startup-prune + thp-always + nav-cap16 lane is the most plausible candidate to actually beat `baselayer-firecracker-headless-shell` total lifecycle without compatibility loss. Build it as a new experimental rootfs/profile pair and run the same `c1/4/8/12/16/24` API matrix before promoting.
4. **Active-navigation admission control profile sweep.** Already listed as "still worth exploring" in [optimization-experiments-log.md](./optimization-experiments-log.md). The harness already supports nav-cap; what is missing is a clean three-profile sweep at `BENCH_NAV_CAP=12,16,20` over `c24/c36` with the BrowserArena-valid path (`domcontentloaded`, no request blocking) so we can attribute the change to admission control, not data-url shape. Expected upside: lower `page_goto` p95 at high concurrency.
5. **Extend the warm-lane winner into broader valid runs rather than inventing more warm levels.** The page-ready matrix on 2026-04-20 showed that `baselayer-firecracker-headless-shell-cdp-warm-density` already beats `baselayer-firecracker-headless-shell` across `c1/c12/c16/c24` on the same host ([page-ready-snapshot-results-2026-04-20.md](./page-ready-snapshot-results-2026-04-20.md)). The next useful warm experiment is not another snapshot shape; it is a broader BrowserArena-valid rerun of those two profiles with the same semantics and a longer sample size.
6. **Prune dead-end profiles from the variant build matrix.** The screening run on 2026-04-15 showed `Krabby`, `Kingler`, `Horsea`, `Seadra`, `Goldeen` did **not** beat their parents. Removing them from `scripts/bench/build-firecracker-rootfs-variants.sh` cuts rootfs build time and avoids polluting comparison tables. The chroot-cache change reduces the cost per variant, but the cheapest variant is the one we do not build.
7. **Move `irqbalance` ban + RPS pinning into the bare-metal start script as a default**, since `irq-housekeeping` was rejected only as an *additional* tuning, not as a baseline. The `thp-always` test already showed host-tuning wins are real but small; consolidating them into `start-baselayer-baremetal.sh` eliminates the variance of "did the operator remember to do step N" between sessions.
8. **Do not pursue more "kernel-flag" cargo-cult variants without a hypothesis.** The `kernel-feature-prune`, `kernel-balanced`, and `kernel-startup-prune-lite` results clustered tightly within `~50 ms` of each other and the kernel-startup-prune row was the best of the bunch by a slim margin. Adding more flag combinations is unlikely to beat a `Gengar + host tuning + nav-cap` stack. Prefer experiments 1-5 first.
